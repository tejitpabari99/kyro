## 2. Two new small source hooks, and why they were needed (M5-10 Part 1)

Three legitimate gaps surfaced while trying to author flows 5/6 honestly against real source —
each is what let the flow actually be written rather than skipped or faked. All three follow
this repo's own established `__DEV__`-gated-debug-hook precedent (`TimerPill.tsx`'s
`-debug-notification-id` hook, added for flow 07) or its "always-present testID" precedent,
never behavior changes:

- **`HevyImportScreen.tsx`'s mocked-picker bypass** (`devFixtureImportEnabled` prop, default
  `false`, combined with `__DEV__`) — the real "Choose CSV File" button calls `pickFile()`
  (`lib/hevy-import-file.ts`), which lazily `require()`s `expo-document-picker`; on this
  sandbox (no native module, and Maestro itself has no way to drive a real OS picker sheet
  either) it always resolves `null`, making the import entry point completely unreachable by
  any E2E flow before this task. The bypass writes the bundled fixture
  (`src/domain/__fixtures__/hevy-import/sample-csv-content.ts`, a generated byte-for-byte TS
  copy of `sample.csv`, drift-guarded by its own test) to a real cache file via
  `lib/csv-export-file.ts`'s `writeCacheTextFile`, then feeds that file's real `uri` through
  the *exact* same `importService.preview(uri)` call the real picker path takes — `preview()`/
  `confirm()` are untouched. Gated on the new prop, not bare `__DEV__`, specifically because
  `HevyImportScreen.test.tsx` already asserts on `pickFile()` being called with its own mocked
  uri, and Jest's own test environment also sets `__DEV__ = true` — a bare `__DEV__` check
  would have silently diverted every one of those existing tests onto the fixture path instead.
  Confirmed this doesn't happen: `HevyImportScreen.test.tsx` (14 tests) still passes unchanged,
  `hevy-import-file.test.ts` (7 tests, `pickFile`/`readTextFile` against a fully mocked native
  layer) still passes unchanged.
- **`settings-debug-theme-mode`** (`app/(tabs)/profile/settings/index.tsx`) — before this task,
  nothing anywhere exposed which theme preference (`system`/`light`/`dark`) is actually active
  as inspectable text; a Maestro flow had no way to assert a theme toggle "took." A `__DEV__`-
  gated `<Text>` under the THEME segmented control renders the raw `settings.theme` value
  already read into the screen. `app/__tests__/settings-theme-e2e.test.tsx` (2 tests) still
  passes unchanged.
- **`CalendarMonth.tsx`'s `${testID}-weekday-${index}`** — the 7 weekday-header cells had no
  testID at all (plain `<Text>`), so a first-day-of-week change (which genuinely reorders these
  labels, `calendar-month-model.ts`'s `weekdayLabels()`) had no stable per-cell handle to
  assert against. Unlike the two hooks above, this is a **pure additive testID, not
  `__DEV__`-gated** — every other testID in this codebase is unconditionally present; only
  debug-only *extra state* gets the `__DEV__` gate. `CalendarMonth.test.tsx` (confirmed still
  green) exercises the chevron-paging path unaffected by this addition.

## 3. Maestro flow 5 (08 §6 item 5) — authored, testID-verified, not executed

New file: `e2e/flows/05-hevy-import.yaml`. Import the bundled fixture CSV via the new mocked-
picker hook → preview screen shows deterministic counts (`"Import 4"`, the one malformed row
at its real line number 16, the NEW CUSTOM EXERCISES card) → confirm → report screen → History
tab populated → a PR badge visible.

**Deliberate choices, explained in the flow's own header:**
- Preview-screen assertions use only values independent of the app's exercise-library match
  state (workout count, malformed-row count, the confirm button's own `"Import 4"` label) —
  not the specific matched/unmatched exercise split. The fixture's 10 distinct titles were
  checked directly against the real vendored `assets/exercise-db.json` (873 entries) at
  authoring time: only `"Incline Dumbbell Press"` and `"Sled Push"` match an existing
  name/alias exactly (case-insensitive); the other 8 are guaranteed unmatched on a real fresh
  install. `hevy-import-service.test.ts`'s own "4 built-ins matched" unit test pre-seeds its
  own controlled 4-exercise library — a real but deliberately different scenario from what
  Maestro would actually see, so this flow does not reuse that split.
- "PRs visible" is asserted via a list-level `text: ".*🏆.*PR.*"` regex, not a specific card —
  reasoned from `history-list-model.ts`'s `buildHistoryCard` (sums every `RecordAward` whose
  `workoutId` matches that card): on a fresh install this import *is* the entire history, so
  every one of the fixture's 10 distinct exercise titles gets its first-ever occurrence in one
  of these 4 workouts, and a first-ever eligible set trivially sets a record in every category
  that exercise type is eligible for. Multiple cards are expected to show a PR badge; which
  ones is not hard-coded.

Every testID/text selector confirmed present in real source at authoring time — full file:line
audit table in the flow file's own header.

## 5. Data-integrity audit (08 §7, M5-10's own "How" line)

New file: `src/test/fixtures/__tests__/data-integrity-audit.test.ts` — a real, automated,
deterministic Jest test, not a manual/one-off claim, per this task's own instruction and the
honesty-over-fabrication posture `docs/plan/BLOCKERS.md` establishes throughout.

Reuses `src/test/fixtures/__tests__/csv-round-trip.test.ts`'s own harness (`generateSyntheticHistory`
+ `insertSyntheticHistory`, real `better-sqlite3` `SqliteDriver`, the same `expo-file-system/legacy`
in-memory mock) against a fixed `now` (`2026-07-25T12:00:00.000Z`) and `generateSyntheticHistory`'s
own default seed (`0x5eed1e55`) — fully deterministic run to run, the same 1040-workout/5-year
dataset the M4-11/M5-08 perf tests already use. Picks 10 workout ids as evenly-spaced indices
across `synthetic-workout-0..1039` (first, last, 8 stops in between) — a fixed, reproducible
slice, not `Math.random()`.

For each: `workoutRepository.getFull(id)` — the exact call `HistoryDetailScreen.tsx` makes — is
the in-app reference. `CsvService.exportWorkout(id, {weightUnit: 'kg', distanceUnit: 'km'})`
(canonical storage units, so no conversion arithmetic needed) is exported, its CSV text
re-parsed via the real, independently-tested `domain/hevy-import.ts` parser (used purely as a
read-only comparison oracle, same posture `csv-round-trip.test.ts`'s own round trip 2 already
established for the identical parser). Every meaningful field is diffed: title, date/time
(floored to the minute — the CSV format's own `d MMM yyyy, HH:mm` has no seconds column, the
one legitimate formatting-only difference this test accounts for), description, exercise
names, notes, set count, weight/reps/duration/RPE per set (exact match, small epsilon for
floating-point noise), distance (±5 m tolerance — `formatDistanceKm`'s own 2-decimal-km/10 m
rounding granularity), and superset grouping (by partition equivalence, same convention
`csv-round-trip.test.ts` already uses).

**Result: green, first try, no diffs found.** 1 suite, 1 test
(`"exports each of 10 deterministically-picked fixture workouts and matches
WorkoutRepository.getFull field-by-field"`), part of the full-suite run below. This is the
audit deliverable itself — a permanent, CI-running regression guard against a future
`csv-codec.ts`/`hevy-import.ts`/`csv-service.ts` change silently breaking the export↔in-app-
history correspondence, not a one-time finding.
